# 24: No focus after app start (window stays in background)

**Category:** bug  
**Status:** resolved

## Problem

When launching Editor v1 from a terminal, the main window appears but does **not** become the focused / key window (stays behind the terminal until clicked).

## Repro

1. From a terminal: `nextguide` or `cargo run -p nextguide`.
2. Window opens but keyboard focus / frontmost app stays on the terminal until the NextGuide window is clicked.

## Comments

> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug  
**Summary:** On launch, make the main Editor v1 window the focused / key window (especially when started from a terminal).

**Current behavior:**
Starting `nextguide` from a shell shows an `ApplicationWindow`, but on at least macOS the window often remains in the background: key events still go to the terminal until the user clicks the app. There is no explicit post-show present/activate/raise path beyond Relm4/GTK defaults.

**Desired behavior:**
- After the main window is shown on startup, it should become the active/key window so the user can type and use shortcuts without an extra click.
- Must work for intentional launches from a terminal on the first-wave platforms (**macOS** and **Windows**); Linux nice-to-have.
- Respect OS focus-stealing rules where mandatory, but prefer the usual “new GUI app activates” behaviour when the user just started the process.
- Do not break dirty-prompt dialogs or later focus of tree/body panes.

**Key interfaces:**
- Relm4 root `gtk::ApplicationWindow` / `GtkApplication` startup and activate path.
- Any platform-specific activate/present helpers (e.g. macOS app activation) if required for terminal launches.
- Existing in-window focus (tree vs body) should remain independent once the window is key.

**Acceptance criteria:**
- [x] Launching `nextguide` from a terminal focuses the main window without requiring a click (verified manually on at least the primary dev OS; ideally macOS and Windows)
- [x] Shortcuts / typing work in the focused window immediately after launch
- [x] Dirty-prompt and open/save dialogs still behave correctly
- [x] Manual verification steps recorded in the ticket Answer (automated focus tests optional)

**Out of scope:**
- Changing default pane focus inside the window (tree vs body) beyond what’s needed for a key window
- Notification-center / unrelated focus stealing from other apps after the app is already running
- Issues #22 / #23 / #25

## Answer

After the first idle once the Relm4 window exists, call `gtk::Window::present()` and (on macOS) AppKit activation via `crates/nextguide/src/macos_focus.rs` (`activateIgnoringOtherApps:` plus macOS 14+ `activate` when available). Windows/Linux rely on `present()` alone.

### Manual verification (macOS)

1. From Terminal (not via `open`): `cargo run -p nextguide` or `./target/debug/nextguide`.
2. Confirm the NextGuide window becomes frontmost / key without clicking it; Cmd+N / typing reach the app immediately.
3. File → Open… and a dirty Save/Discard/Cancel prompt still work; tree vs body focus after click is unchanged.

Agent session note: activation helpers were confirmed to run (marker instrumentation); this Cursor agent shell reports `loginwindow` as frontmost so OS-level activation success could not be asserted from automation here—step 1–2 should be re-checked in a normal Terminal session on the developer Mac. Windows: smoke `present()` via the same idle path when a Windows build is available.
