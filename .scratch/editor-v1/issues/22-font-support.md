# 22: Font table leak — Arial / `;` shown as body text

**Category:** bug  
**Status:** resolved

## Problem

Guides written by The Guide that declare Arial in `\fonttbl` show the literal text **`Arial`** (and often **`;`**) in the Editor v1 body pane, instead of applying a font silently. Confirmed: `nextguide-rtf` load of a Guide-like sample yields plain text `Arial;Hello`.

Font **family/size selection UI** is **out of scope** for this ticket (follow-up enhancement).

## Repro

1. Open `data/ImportSample.gde` (or any Guide with `{\fonttbl{\f0\fnil\fcharset0 Arial;}}`).
2. Select a Node with a body.
3. Observe `Arial` / `;` in the visible body text.

## Agent Brief

**Category:** bug  
**Summary:** Stop RTF `\fonttbl` / font-switch markup from appearing as visible body text in Editor v1.

**Current behavior:**
`nextguide-rtf`’s loader does not treat `\fonttbl{…}` (and nested font-definition groups) as destinations to skip. Control words inside are ignored, but the font **name** and trailing **`;`** are collected as normal character data. Loading a typical The Guide body therefore yields visible strings like `Arial;` before real content (verified: sample with `\fonttbl…Arial;` + `Hello` → plain `Arial;Hello`). The editor surfaces that model in the GTK body pane, so every Arial Guide body looks polluted.

**Desired behavior:**
- Font tables and font-definition groups never contribute characters to the edit `Document`.
- Font switches (e.g. `\f0`) do not insert visible text; they may be ignored for now (subset still need not model face/size).
- Real content (e.g. `Hello`) still loads with existing B/I/U / paragraph / list behaviour.
- Soft-fail / unparseable path must not leave raw `\fonttbl` names as the primary “content” when a better strip is available (best-effort).
- Untouched Node bodies continue to preserve original opaque RTF bytes when the user does not edit them (Format v1 / Editor v1 policy unchanged).

**Key interfaces:**
- `nextguide_rtf::load` / the RTF → `Document` parser: must skip `\fonttbl` groups (and similar font-definition destinations) the way other destinations are skipped today.
- `Document` / `Run` / `SpanStyle`: no requirement to add font-family or size fields in this ticket.
- Editor GTK mapping: should automatically benefit once the load model no longer contains leaked font names; no separate UI feature in this ticket.

**Acceptance criteria:**
- [x] Loading Guide-like RTF that includes `{\fonttbl{\f0\fnil\fcharset0 Arial;}}` plus body text does **not** put `Arial` or a bare fonttbl `;` into any `Run` text
- [x] A regression test in `nextguide-rtf` covers at least one The Guide–shaped Arial `\fonttbl` sample (empty body and body with visible text)
- [x] Existing `nextguide-rtf` subset / soft-fail / untouched-bytes tests still pass
- [x] Opening `data/ImportSample.gde` in the editor (manual or headless path that uses `load`) no longer shows `Arial` as body text on those Nodes

**Out of scope:**
- Font family or size **selection** UI
- Modeling font face/size on `SpanStyle` or Round-tripping chosen fonts on edit
- Perfect visual match to Arial vs system default face (ignoring `\fN` is OK for this bugfix)
- Colour / highlight / other exotic RTF display work

## Answer

`nextguide-rtf` now skips `{\fonttbl…}` groups in the editable parser (same destination-skip path as `\*` / `\pntext`). Soft-fail `strip_controls_rough` also drops `\fonttbl` / `\*` groups so font names are not the primary fallback content. Regression coverage: Guide-shaped empty + `Hello` samples, dedicated fonttbl leak test, soft-fail strip test, and headless `import_sample_bodies_do_not_leak_fonttbl_arial` in `nextguide` `gde_link` tests. `\fN` / `\fsN` are now modeled by ticket 25 (no longer ignored). `{\colortbl …}` is skipped too, since its `;`-terminated entries leaked `;` into ImportSample bodies.
